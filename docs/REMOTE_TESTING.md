  # Remote testing

Two ways to let a teammate test the app. Prefer **Option A (everything on Render)** —
no machine of yours needs to stay online. Option B (local backend behind a tunnel) is
kept for when you want the local database or provider setup.

## Option A — full stack on Render (recommended)

```
Teammate's browser
   │  https://ideaforge-clxe-fl5k.onrender.com        (static SPA, fast CDN)
   ▼
Render edge ──serves assets──► frontend/dist
   │  /api/*  rewritten server-side (proxy)
   ▼
https://ideaforge-api-6161.onrender.com          (Spring Boot, dev profile, Frankfurt)
   │
   ▼
Render Postgres `ideaforge-db` (internal network only)
```

[`render.yaml`](../render.yaml) at the repo root defines all of it:

| Resource | What it is | Notes |
| --- | --- | --- |
| `ideaforge-db` | Render Postgres, free, Frankfurt | Fresh DB; Flyway migrates and the dev seeder creates `test1`–`test3` with 100 credits each. Internal connections only. |
| `ideaforge-api-6161` | Docker web service, free, Frankfurt | Runs the **dev profile**: fixed OTP `000000`, Turnstile disabled, peppers generated by Render. Health check `/actuator/health/readiness` (the aggregate reports DOWN only when SMTP is unreachable, which never blocks serving). |
| `ideaforge-clxe-fl5k` | Static site created by Render | The plain `ideaforge-clxe` name was already taken by the earlier manual site, so Render created this one with a `-fl5k` suffix. `CORS_ALLOWED_ORIGINS` and `APP_BASE_URL` must match this URL. **The `/api/*` rewrite must point at the API service** — pointing it at the site itself answers with empty 200s and logins only appear to work. |

### Deploy or update

1. Push `render.yaml` to the default branch.
2. Render Dashboard → **Blueprints**:
   - no Blueprint yet: **New** → **Blueprint** → pick this repo. Render reads `render.yaml`.
   - already linked: open the Blueprint and **Sync**.
   - If a static site name is already in use, Render creates the new one with a random
     suffix (here `ideaforge-clxe-fl5k`); `CORS_ALLOWED_ORIGINS`, `APP_BASE_URL`, and the
     verification URLs below must match its actual URL.
3. Review the sync preview before applying: it should create the API service and database
   (or update them) and leave the static site's rewrite pointing at
   `https://ideaforge-api-6161.onrender.com/api/*` — never at the static site itself.
   When prompted, paste your `DEEPSEEK_API_KEY`.
4. Wait for the first API build (~5–10 min; it compiles with Maven in Docker) and for the
   service status **Live**.
5. Verify the proxy from your machine:

   ```bash
   curl -i https://ideaforge-clxe-fl5k.onrender.com/api/fields
   # expect: HTTP 401 with JSON body {"code":"UNAUTHORIZED",...}
   ```

6. Log in at `https://ideaforge-clxe-fl5k.onrender.com` with `test1@ideaforge.test`,
   `test2@ideaforge.test`, or `test3@ideaforge.test` and code **000000**.

### Things to know

- **This is a test environment.** The dev profile keeps the fixed OTP, open Swagger docs,
  and no Turnstile. Do not put real user data in it.
- **Free plan behavior:** web services sleep after ~15 minutes idle — the first request
  wakes the backend and can take about a minute. The free Postgres instance is small
  (1 GB) and Render expires free databases after a while (check Render's current limits);
  re-syncing the Blueprint recreates it, and the seeder repopulates the test users.
- **No mail server:** OTP emails fail to send (connection refused, only logged); the fixed
  code still works because the code row is stored before sending.
- **SearXNG is disabled** here (`SEARXNG_ENABLED=false`), so research uses Hacker News and
  page fetches only. Production keeps SearXNG via `infra/docker-compose.prod.yml`.
- **LLM settings** live as plain env vars in `render.yaml` (DeepSeek `deepseek-chat` for
  all four purposes). Edit and sync to switch; add `OPENAI_API_KEY` etc. as needed.
- **Region is permanent** (`frankfurt`), chosen for your location; the database and API
  must stay in the same region.
- **If the API service name is already taken**, Render assigns a different URL — update the
  `/api/*` rewrite destination in `render.yaml` and sync again.
- **The earlier manual static site** (`ideaforge-clxe.onrender.com`, rewrite to ngrok) is no
  longer used — delete it in the Render dashboard once the new site works, and stop the
  ngrok tunnel.
- **Database access:** internal only. To inspect it from your machine, temporarily add your
  IP in the database's **Access Control** tab in the Render dashboard.

## Option B — local backend behind a tunnel (fallback)

For when you want testers on your local database, mailpit, or the SearXNG instance.

```
Teammate's browser
   │  https://ideaforge-clxe-fl5k.onrender.com
   ▼
Render edge ──serves assets──► frontend/dist
   │  /api/*  rewritten server-side (proxy)
   ▼
https://<your-tunnel-host>  ──►  localhost:8080  (Spring Boot, dev profile)
```

### 1. Local stack

```bash
cd /home/fat-joe/projects/ideaforge
docker compose up -d                            # postgres 5433, mailpit, searxng
cd backend && ./mvnw spring-boot:run -Dspring-boot.run.profiles=dev
```

### 2. Expose the backend through a tunnel

Point the tunnel at **8080** (not 5173).

```bash
cloudflared tunnel --url http://localhost:8080   # preferred; no interstitial page
# or
ngrok http 8080                                  # free dev domain stays stable
```

A stable tunnel host matters: a random URL means updating the static-site rewrite each run.

### 3. Point the static site at the tunnel

If the site is Blueprint-managed (Option A), edit the `/api/*` rewrite destination in
`render.yaml` to `https://<tunnel-host>/api/*`, push, and sync. Otherwise edit it directly
in the site's **Redirects/Rewrites** tab in the Render dashboard. Either way order matters:

1. Rewrite: `/api/*` → `https://<tunnel-host>/api/*` (full URL)
2. Rewrite: `/*` → `/index.html` (SPA client-side routing)

Fallback hosts (Cloudflare Pages, Netlify, Vercel) with the same two rules are documented in
`frontend/public/_redirects.example`.

### 4. Why the API must be proxied

Calling the tunnel directly from the browser would make the session and CSRF cookies
third-party — Safari blocks them and Chrome increasingly does too, so login would fail no
matter how CORS is configured. The server-side rewrite keeps every request same-origin.

## What to give the teammate

- URL: the static site (assets load from the CDN; only API replies are tunneled in Option B).
- Login: seeded accounts (`test1`–`test3@ideaforge.test`) and the **dev OTP `000000`**.
  Use the seeded accounts: behind a tunnel every request shares one apparent IP, so the
  signup throttle (3 accounts/IP/24h) is shared by everyone.
- Limits: 10 generations/day and 200 chat messages/day per user, plus the global daily LLM
  budget (`LLM_DAILY_BUDGET_USD`, default $10). A 503 means the budget tripped.
- Costs: generate 2 credits, chat 0.2/message, re-validate 0.5, finalize 1. Seeded test
  users start with 100 credits. **On Option A each restart does not re-grant** — seeding is
  idempotent — so if a user runs out, create a new account or adjust via the DB.

## Shared gotchas

- **403 FORBIDDEN on a POST**: a stale CSRF cookie. Refresh the page; if it persists see
  `D39` in `docs/DECISIONS.md`. On Option B the tunnel request log
  (`http://127.0.0.1:4040` for ngrok) shows the real status codes.
- **Balance and ideas look empty but login works (Option B, ngrok free)**: ngrok's
  interstitial can replace browser-style GET responses with HTML at status 200. The SPA
  sends `ngrok-skip-browser-warning: true` on every request to bypass it
  ([ngrok docs](https://ngrok.com/docs/pricing-limits/free-plan-limits/#removing-the-interstitial-page));
  a tunnel-side workaround is not allowed on free plans. `cloudflared` has no interstitial.
- **Dev-only settings** (fixed OTP, Turnstile disabled) exist only in the `dev` profile —
  never tunnel or host a `prod`-profile backend with them, and never expose
  Mailpit/SearXNG/Postgres tunnels publicly.
